## 审计发现

### P1｜目录保存会永久删除已有深度分析

**证据：**`backend/app/services/rag/toc_editor.py:143` 无条件删除该书的 `BookDeep`。此表保存逐章总结、Markdown、阅读卡和增量哈希缓存。人工保存、自动修正、历史恢复以及单书或全库目录重识别都调用同一个替换函数。`frontend/src/views/ReaderView.vue:348` 更新目录后没有重新加载深度分析，当前页面还会暂时显示已从数据库删除的旧产物。

**复现：**在隔离数据库中先保存一条状态为 `done` 的深度分析，再修改一个目录标题。保存后，`BookDeep` 查询结果为空。即使只修正标题且原文未变，产物也会删除。目录修订快照仅含目录，不能恢复阅读卡或总结。

**影响：**用户可能在批量重识别目录后失去大量已付费生成的内容和可复用缓存，界面关于“可恢复修订”的提示会产生误解。

**建议：**将深度分析改为保留原产物并标记来源版本失效。保存目录时只使受影响章节的映射失效；完成重算后再替换展示版本。若必须删除，先保存可恢复快照，并在执行前明确列出会失去的产物。目录保存成功后立即刷新阅读器的深度分析状态。

### P1｜目录数据库与全文索引不具备一致的提交边界

**证据：**`backend/app/services/rag/toc_editor.py:154` 先提交章节、分块归属与修订；第 159–161 行随后删除旧索引，并逐块使用独立事务写入。索引删除或任一分块写入失败时，接口返回错误，但数据库修改已经生效。逐块失败还会留下不完整索引。

**复现：**在隔离数据库中模拟索引删除抛错。调用方收到 `simulated FTS failure`，但目录标题已变更、修订已生成，原有深度分析已删除。

**影响：**用户可能重复点击保存；检索结果可能漏掉分块或继续显示旧章节归属，来源定位与目录不一致。

**建议：**以单本书为单位批量重建索引，并将数据库改动与索引更新置于同一 SQLite 事务；若索引必须异步更新，则持久化 `index_pending/index_failed` 状态，失败后自动重试，并在完成前避免展示不可信的检索结果。

### P1｜重复 AI 任务的拦截存在竞态

**证据：**`backend/app/api/assistant.py:230–237`、`backend/app/api/deep.py:228–230`、`backend/app/api/sensemaking.py:491–493` 都先调用 `has_active_task`，之后才调用 `submit`。`backend/app/worker/tasks.py:244` 只保护注册表插入；查重与插入没有共同的锁或数据库唯一约束。

**触发条件：**同一资料的两个请求在查重后、任一个提交前交错执行。两次检查都得到“无任务”，随后各自入队。助手批量研读还会扩大这一窗口。

**影响：**重复调用模型并计费，两个任务可能并发写同一产物，最后完成的结果覆盖先完成的结果。此项由代码路径推导，尚未进行并发压力复现。

**建议：**提供按 `(任务类型, 资料 ID, 来源版本)` 原子占位的提交接口。用同一临界区完成查重和注册，必要时增加数据库唯一约束与幂等键；批量提交应一次性预占所有资料。

### P1｜本地 API 接受任意域名的“同源”请求（有条件的安全风险）

**证据：**`backend/app/main.py:311–322` 在 `Origin` 的主机名等于请求的 `Host` 时直接放行，没有校验该 `Host` 是否属于本地地址或明确配置的部署域名。默认服务绑定 `127.0.0.1`，API 没有用户认证。测试客户端将两者同时设为 `example-attacker.test:8000` 时，`/api/health` 返回 200；只改变 `Origin` 时返回 403。

**触发条件与影响：**若攻击者能使浏览器通过其控制的域名访问本机服务（例如 DNS 重绑定），浏览器会把请求视为该域名的同源请求。此时来源检查不能保护个人知识库中的读取与修改接口。该项已验证主机校验缺口，尚未进行浏览器和网络环境中的完整攻击复现。

**建议：**本地运行时只接受 `localhost`、`127.0.0.1` 和明确批准的主机名；部署模式从配置中读取可信主机与可信代理，不以任意 `Host` 或未经验证的 `X-Forwarded-Host` 推导信任。增加恶意 `Host`、相同 `Origin` 的拒绝测试。

### P2｜无效书籍编号会使带范围的搜索变为全库搜索

**证据：**`backend/app/api/books.py:992–996` 将无法解析的 `book_ids` 设为 `None`。随后第 1026 行传给检索器；`None` 表示不限制书籍。比如 `book_ids=12,abc` 会忽略原有范围并检索全库。

**影响：**调用方收到超出所选资料的搜索结果，可能在写作时误用其他书籍。当前项目助手问答有独立的范围解析，不受这条搜索入口直接影响。

**建议：**对非法编号返回 422；明确区分“未提供范围”和“提供了无效范围”。补充 API 回归测试，验证任何解析失败都不会扩大检索范围。

### P2｜自定义模型连接忽略单次问答的模型选择

**证据：**`backend/app/api/chat.py:89–90` 只把请求中的 `model` 写入 `deepseek_model`。`backend/app/services/llm/__init__.py:525` 对自定义连接读取的是 `model` 字段。隔离构造中，请求模型为 `requested-model`，实际创建的连接仍使用 `configured-model`。

**影响：**用户选择不同模型后，自定义连接仍使用配置的默认模型；显示的预期模型与实际调用可能不一致。

**建议：**统一使用规范化的 `model` 覆盖字段，模型初始化和响应元数据均读取同一个值；限制单次覆盖为该连接允许的模型，并分别测试 DeepSeek 与自定义连接。

### P2｜深页搜索的总数与可达结果不一致

**证据：**`backend/app/api/books.py:1025` 把检索候选截断为最多 200 条，第 1029 行却将已截断的结果长度当成 `total`。这不是匹配总数，且第 201 条以后的结果无法翻页取得。

**影响：**大型个人知识库中，用户会误以为只找到 200 条或更少；深页检索缺失。

**建议：**将 `total` 定义为真实过滤后总数；若混合排序无法给出真实总数，返回 `has_more` 和明确的候选上限，并提供继续检索的游标或更窄的筛选入口。

### P3｜任务标记完成时不统一收敛进度

**证据：**`backend/app/worker/tasks.py:176` 将任务置为 `done`，但不设置 `progress=1.0` 或完成阶段。已有部分任务自行设置进度，未自行设置的任务会留下类似“已完成、94%”的持久化状态。

**影响：**任务 API、历史记录和依赖进度判断的界面可能互相矛盾。

**建议：**由任务管理器在成功结束时统一写入 `progress=1.0`，再持久化完成状态；取消和失败保留实际进度。

## 修复顺序

1. 先阻止目录操作删除深度分析，并修复索引更新的提交与恢复机制。两项会影响既有用户资料和来源可信度。
2. 同批修复本地主机校验，并将 AI 任务查重改为原子提交，分别控制资料访问和重复计费风险。
3. 随后修正搜索范围解析、模型覆盖和分页语义。
4. 最后统一任务完成进度，补充上述边界的回归测试。

## 验证边界

本次是代码审计和隔离复现，没有对真实 PDF 批量重识别、实际供应商并发计费、DNS 重绑定或超大文献库分页执行端到端测试。并发风险与深页表现分别由调用顺序和明确的 200 条截断逻辑推导；正式修复时应加入有屏障的并发测试和超过 200 条结果的样本测试。
