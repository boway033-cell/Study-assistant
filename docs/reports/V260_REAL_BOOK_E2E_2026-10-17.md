## 5. 发现并修复的两处阻断缺陷

### F1 · 研究报告在第一个模型调用即失败（ContextVar 跨 Task）

**现象**：**study-overview-75a4ceba** 在 **research-plan** 阶段失败：

    ValueError: <Token var=<ContextVar name='current_ai_task_budget' ...>>
    was created in a different Context

**原因**：任务 worker 在协程外层设置 **current_budget**；**RoutedProvider.stream_chat** 又在异步生成器内部 set/reset；**_stream_answer** 用 **asyncio.create_task(anext(iterator))** 推进生成器，下一次恢复发生在另一个 Task 的 Context 中，**reset(token)** 因此抛错。普通问答直接 **async for** 消费，所以只有研究报告/审计任务暴露。

**修复**：由调用方持有 ContextVar 生命周期，删除生成器内部的 set/reset（**backend/app/services/llm/__init__.py**）。新增回归：**test_stream_handles_consumer_advancing_in_separate_tasks**。

### F2 · 真实 PDF 的 C0 控制字符让精确引文被判“未匹配”

**现象**：真实 chunk 含 **\x03**（PDF 版面清洗遗留）。审计模型返回的引文已去掉控制字符，而来源原文保留，**_quote_key** 归一化后不相等，导致 **matched=false**、claim 从 **supported** 降为 **needs_review**，界面显示“未匹配所给材料”。

**修复**：**_quote_key** 额外移除 **\x00-\x1f** 与 **\x7f**（**backend/app/services/research_audit.py**）。新增回归：**test_pdf_control_characters_do_not_break_quote_matching**。

> 这两处都不是模型质量问题：前者让任务根本无法启动；后者会让真实 OCR/PDF 库上的“原文核查”系统性地把正确引文判错。
