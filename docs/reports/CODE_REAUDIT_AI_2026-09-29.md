## 结论

上轮审计的 P3 问题已修复：任务成功结束时，后台统一保存完成状态、100% 进度、完成阶段和完成文案；任务中心按最终状态显示，不再把运行中的提示留在已完成任务上。启动恢复也会规范旧的完成记录。上轮 P1、P2 修复路径已随本轮全量测试再次回归。此次审查的范围内，没有发现需要立即停止使用的新增故障。

AI 处理流程现在形成了更清楚的闭环：**确定资料与模型范围 → 估算预算 → 阅读和检索 → 形成可见研究计划 → 按证据需求补取原文 → 分段成文 → 核对主张与来源 → 保存并供人工修订**。独立写作和综述复用来源边界、长文续写、引文转换及中文风格审计。这里的“研究计划”和“主张审计”是可复查的工作产物；模型的隐性推理内容不写入报告。

## 功能安排评估

**资料理解。** 用户选择书架、项目、书目或章节后，系统在选定范围内阅读与检索；恢复原文证据时只纳入已读锚点。该设计支持“以自己的资料为依据”的助手目标。全文阅读后的证据需求核查增强了长篇书目的论点定位，但它只能证明有候选片段，不能自动证明主张成立。

**思考逻辑。** 深度研读先产出子问题、分析维度、证据需求和报告提纲，再分段写作、生成主张台账。段落主题与人工待核查项可见，便于发现跳步、重复和缺证。短报告保持一次综合生成；长报告分段，避免大 JSON 被模型输出上限截断。独立新作把 Writing DNA 作为表达与结构校准，事实只能从本次明确选中的来源取得。

**文本生成。** 提示词强调主张前置、每段只推进一个论证单元、引用可定位、保留冲突与真实限制，随后进行中文格式与风格审计。输出质量仍受材料质量和模型能力影响；代码能拦截空稿、截断稿、格式损坏和无效锚点，却不能凭格式检查证明论证正确。用户仍需在主张审查区回到原文确认。

**速度与成本。** 解析队列与交互 AI 队列分开；不同任务可以并行，单模型连接有并发上限。预估显示调用和文本规模，并固定用户确认时的模型路由。深度模式和长文续写会增加调用次数；页面应继续清楚显示当前阶段与已生成草稿。

## 验证结果与边界

- 后端全量测试：`467 passed, 1 skipped`（最终回归时记录）。新增用例覆盖 P3 完成态、流式终止与安全拒绝、预算中的思考增量、写作续写、长书证据需求、段落分工、损坏 JSON 拒绝入库及路由漂移。
- 前端单元测试：`92 passed`；生产构建通过。研究页新增段落分工显示已通过构建检查。
- 固定检索评测集通过既有阈值：`Recall@1=0.9706`、`Recall@3=0.9902`、`Citation correct=0.9804`、无答案拒答率 `1.0`。这些指标只验证该固定样本集中的检索与锚点行为，不代表所有真实书目的生成质量。
- 使用模拟 HTTP 流核对三种协议。没有实际调用 DeepSeek、Anthropic、Gemini 或自定义网关，因此端点兼容性、真实延迟、账单与供应商特有事件仍需在用户配置的连接上做一次端到端验证。

## 下一步优先事项

1. **P2：建立真实书目写作评测。** 从长篇书目、跨书目冲突、稀疏证据、扫描 OCR 和中英混排中各取样。人工标注论点是否被原文支持、反例是否遗漏、段落是否重复、标题结构是否服务论证，再按固定版本比较模型与提示词。当前自动检索分数不能替代这项评测。
2. **P2：细化实际用量记录。** 接入各供应商可返回的实际 usage，展示生成 token、思考 token、费用和重试/续写调用数；对没有 usage 的兼容网关继续标注“估算”。目前按字符折算的预算可限制本机任务，但不等于供应商账单。
3. **P3：把主张审计失败设为醒目的报告状态。** 当前长报告的正文可保留，失败原因写入“待继续核查”；后续可单独提供“重跑来源审计”，并在人工确认前避免把这些主张视为已核实事实。

这三个方向的优先级来自本次代码复审和验证边界；其中真实书目评测最能判断“读懂资料并写出有深度的文章”是否真的成立。
