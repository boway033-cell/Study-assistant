## 1. 根因层：五个结构性问题

### 1.1 提示词没有任何治理机制 —— AI 深入开发的头号瓶颈

80 个调用点的提示词是散落在 15 个文件里的 Python 字面量。直接后果：

- **改一个词的影响面不可评估**：没有版本号、没有 A/B、没有回归基线，改完只能靠人眼跑一遍。
- **同类能力三套写法**：分批研读（`long_research.py:66`）、章节精读（`deep_analysis.py:424`）、综述综合（`writing_lab.py:523`）本质是同一件事，措辞与约束各不相同，质量无法对齐。
- **无法做模型迁移**：换模型时没有"提示词 × 模型"的对照实验载体，只能整体试错。

这不是"该写得更漂亮"，是**没有做实验的容器**。所有"AI 更深入"的诉求（更好的综合、更强的论证）最终都会落到改提示词，而改提示词在当前结构下是**盲改**。

### 1.2 结构化输出没有校验与修复闭环

`_call_json`（`writing_lab.py:91`）：调用 → `parse_json_response` → 不是 dict 就 `RuntimeError`。

- 无 JSON Schema 校验（解析成功但字段缺失/类型错，会一路传到下游才炸）
- 无"解析失败 → 带错误信息重试一次"的修复循环
- 无降级（该段用宽松格式兜底 vs 整段报废）

研究报告链路是 **规划 → 分批研读 → 逐级压缩 → 分段成文 → 主张审计** 五段串联，任一段 JSON 失败则整份任务报废。已有逐段草稿保存，但**失败重试粒度是段，不是"这一段的一个 JSON 字段"**。

### 1.3 测试覆盖的是控制流，不是 AI 质量

268 个后端用例全部用 Fake/Stub provider——它们验证"批次数对不对、锚点有没有拼进去、草稿有没有存盘"，无法回答"换了个提示词/模型后，综合质量是不是变差了"。

唯一能量化质量的 `retrieval_v2`（114 题）依赖本地真实库与模型，**在 CI 上不具备运行条件**，实际从未形成门禁。

> 结论：**当前有一张很好的工程安全网，但没有质量安全网。** 这也是"AI 深挖"越做越不敢改的直接原因。

### 1.4 控制流是单轮：规划产出物没有被消费

`api/study.py:452`：`queries = [focus] + plan["subquestions"][:3]` —— 一轮检索，直接进写作。

而**同一份规划的 `evidence_needs`（`:166` 定义、`:413` 要求模型产出）在后续链路里没有任何消费点**。也就是说：

- 规划阶段已经让模型想清楚"需要哪些证据"
- 检索后**没有一步去核对"这些证据找到了没有"**
- 缺口只能以 `needs_review` 的形式在最终报告里事后标注

对照 Undermind 的"递归检索 + 覆盖率估计"、NotebookLM 的迭代研究，这是**控制流代差，不是模型代差**。好消息：`evidence_needs` 的 schema 已经存在，缺的只是消费它的一段分支。

### 1.5 知识图谱是展示层，语义资产没有沉淀为检索能力

`api/graph.py:79-89`：edges 来自 `Counter` 关键词共现权重，无 `contradicts / supports / depends_on` 语义标签，**检索链路完全不读它**。

而 `StudyReport.claims_json` 里其实已经产出了 claim 级的 `synthesis_relation: conflict|consensus|complementary|single_source|unresolved` + `counterpoint`——**语义边的数据源就在库里，只是没被用来建图，也没被用来检索**。

## 3. 架构风险：真正卡住"AI 深入开发"的三件事

### 3.1 SQLite 专用路径深度耦合，Postgres 迁移成本被低估

`MEOO_PERSISTENCE_PLAN` 规划迁 Supabase PG，但代码里：

- **34 处** `PRAGMA` 相关（含 `synchronous=NORMAL` / `busy_timeout` 等性能调优，PG 无对应项）
- **22 处** 手写 `ALTER TABLE`（对应 `_migrate()` 的逐版本演进）

这不是"换连接串"。FTS5 全文检索没有 PG 等价物（需改 `tsvector` 或降级为可再生索引），而 FTS5 正是当前混合检索的一半。**建议：迁移前先把检索栈抽象成接口，否则会边迁边改 AI 主链路。**

### 3.2 成本与并发完全裸奔

- 无 LLM 结果缓存（同一问题重问，重新付费）
- 无并发信号量（用户连点三次"深度研读"= 三倍 token）
- 无预算/配额上限，`llm_usage_stats` 只做事后统计（`llm/__init__.py:289`）不做事前拦截
- 模型 fallback 只在**未产出任何输出前**生效（`RoutedProvider.stream_chat:362`），且无健康度记忆——主模型每次都先试一遍

长任务已经能做 6 分钟、能取消、能恢复，**但没有"这次要花多少钱"的可见性与上限**。这是从"能用"到"敢放手用"的分界线。

### 3.3 单进程 + SQLite 写锁 vs 后台任务并发

后台任务（`worker/tasks.py`）与导入任务（`import_task.py`）并发写 SQLite，靠 `busy_timeout=15000` 兜底。当前单机单用户没问题，一旦上容器多实例或 PG 迁移，任务队列语义需要重新定义。

## 5. 建议：先修容器，再修内容

按"能否让后续所有 AI 改动变便宜"排序。

### 第一步：建 AI 实验容器（不改任何业务行为，纯搭架子）

| 动作 | 成本 | 收益 |
|---|---|---|
| **提示词 registry**：把 15 个文件的硬编码提示词抽成带 id/version 的模块，调用点改为按 id 取 | 中 | 改一个词能定位影响面，能做 A/B，能做模型迁移对照 |
| **JSON 输出 schema 化**：关键链路（规划/审计/去重）加 schema 校验 + 一次带错重试 | 低 | 直接降低长链路报废率 |
| **质量评测进门禁**：`retrieval_v2` 114 题做到能在无外网/小样本下跑，接进 CI 或本地 pre-commit | 中 | 有质量网才敢改提示词 |

### 第二步：把已有资产接成能力（数据都在库里，缺的是消费方）

1. **`evidence_needs` 消费回路**（建议 #3）：检索后加一次"缺口评估"小调用，缺口大 → 补一轮检索或明示材料不足。控制流改动，模型成本增加约 1 次调用。
2. **库级矛盾视图**（建议 #2）：聚合所有 `claims_json` 的 `synthesis_relation`，纯聚合 + 一个前端视图，零新模型。
3. **把 claims 的语义边喂给图谱**（1.5 节）：图谱从"关键词共现"升级为"主张关系图"，进而可参与检索。

### 第三步：工程护栏

- LLM 结果缓存（按 prompt hash + 模型 + 参数）
- 并发信号量 + 单次任务 token 预算上限（超出前提示，不是事后统计）
- 检索栈抽象成接口（为 PG 迁移与 B1 升级同时铺路）

### 不建议现在做

- PRISMA 系统综述流水线（定位漂移，见上一份报告 §2.4）
- 字号 token 化全量替换（225 处跨 25 文件，仍建议按 `LibraryView → ReaderView → PdfReader` 分 3 批 + 截图比对）
- B1 检索栈全量落地（S1–S5 严格串行，第一步先做 S0 评测可插拔，与上面的"质量评测进门禁"是同一件事）

---

## 6. 一句话结论

功能层的欠账都是**局部可修**的；真正卡住"AI 深入开发"的是**没有实验容器**——提示词无法版本化、输出无法校验、质量无法回归。在这三件事补齐之前，任何"让 AI 更深入"的改动都是在盲改，且改完无法证明变好还是变坏。
