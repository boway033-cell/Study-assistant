## 分别分析

### lieflat-gongwen：文体诊断与分阶段写作

主要价值是区分文体后再观察句长、标题层级、标点和措辞强度，并要求先确认提纲、再展开正文。改稿先区分事实、结构与表达问题，适合作为写作台的诊断层，而不是单个万能提示词。

其统计覆盖事务性材料与短经验材料，不包含通知、请示、批复、函等法定公文的统计基线。区间是样本描述，不是国家标准，不应通过强行补字、增加顿号或删除问题来换取“达标”。某些文体的样本量较小；参数卡也存在不同统计口径，接入时必须保留来源、适用文种和局限。

尤其不能把经验材料中的表达取舍泛化为自动隐藏用户提供的不足、风险或未解决事项。

### official-document-skill：文种、事实与审稿

覆盖法定公文和常见机关事务材料。核心是明确发文主体、受文对象、行文关系及办理目的，先整理事实，再按文种组织内容；审稿重点是文种混用、事实缺口、责任时限不清及空泛表达。

适合承担起草、改写和内容检查。需要保留用户原稿的实质信息，缺少的数字、政策、日期、文号和机构信息应列为待补项，不能为了完整版式自动编造。其主观评分不能直接包装成真实性证明或合规认证。

### sanmu-document-formatting：确定性的 DOCX 排版

将正文角色识别、排版配置、文档生成、元数据清理与结构验证分开，支持标题层级、正文、说明、落款、页码等不同角色。处理已有文档时先展示分类及表格方案，由用户确认后执行，且保留原文件。

适合承担 Word 导出和格式配置。其默认全局加粗、字体、行距等属于可配置预设，不能未经核验便称为完整 GB/T 9704 合规。缺失字体不得静默安装；保留表格几何和复杂对象的边界。结构验证与实际渲染验收必须分开显示。

## 需要解决的规则冲突

| 差异 | 产品处理原则 |
| --- | --- |
| lieflat 要求先确认提纲，official 倾向直接交稿 | 默认采用“提纲 → 用户确认 → 正文”，后端校验确认状态；修改事实或文种后使旧确认失效 |
| lieflat 的统计偏好与 official 的自然表达约束 | 事实与办理要求优先；风格指标只给建议，不作为自动删改依据 |
| 文种选择建议不同 | 展示不匹配的原因并让用户确认，不静默改成另一文种 |
| 三套占位与文档展示习惯 | 内部统一待补信息结构；编辑器单独显示清单，导出前明确提醒，不伪造落款或文件编号 |
| 临时格式要求与长期配置 | 本篇覆盖优先；保存默认格式需显示差异并明确确认，不把机构名称、正文或日期存入格式配置 |
| 内容审查与格式验证 | 分开记录事实待核、文种检查、表达建议、DOCX 结构验证和视觉验收，不能用一个总分替代 |

## 推荐融合流程

1. 写作台增加“公文写作”入口，与现有研究写作、Writing DNA 和去 AI 味功能并存，保持当前配色。
2. 输入文种、事项、发文主体、主送对象、行文关系、粘贴的事实材料与篇幅；本次不增加库内知识对象选择器，不自动读取文献作为事实来源。
3. 整理事实清单与缺失项，生成可编辑提纲；确认后才生成正文。
4. 内容审查区区分必须核对的问题与表达建议，允许用户选择改稿范围；每次改写保存版本，不覆盖原稿。
5. 采用独立的公文排版配置导出 DOCX，保留可编辑文本；不模拟印章，不自动补造正式文号。
6. 保留修改历史、来源快照及导出记录；草稿有未核实事实时不得标记“可正式签发”。

现有入口是 `frontend/src/views/WritingView.vue` 和 `WritingLabDrawer.vue`，服务接口位于 `backend/app/api/writing.py`。建议公文编辑区独立为组件、服务与请求模型，复用现有模型路由和输出历史，但不强迫普通公文起草满足 Writing DNA 的二十篇语料门槛。

## 实施后的验收范围

- 文种与行文关系校验、提纲确认失效、待补事实、来源限定及原稿版本保留。
- 模型失败与 150 秒超时不创建成功版本；前端请求等待 180 秒。当前不是后台任务模式，不提供任务取消按钮。
- 公文正文生成、选择性改写、历史回读与 Word 导出闭环。
- DOCX 字体、页边距、标题层级、落款、页码和元数据清理。仅支持新草稿/文本导出；本次不暴露已有 DOCX 上传重排及表格转换入口。
- 三个技能的版本、许可及使用范围记录在每个公文版本审计中；lieflat 仅适用其已有统计基线，不复制全部范文/DNA语料。
- 桌面与窄屏无按钮裁切，保留现有写作台功能；使用虚构资料回归，不上传用户文献。
